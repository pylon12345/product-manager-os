# 产品经理 100 个核心术语

> 本文件是按需加载的术语知识层。不要在每次调用 Skill 时整体加载。遇到术语解释、PRD、指标或 AI 架构相关问题时，只读取相关条目。

## 产品基础

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 1 | **PM（Product Manager）** | 产品经理。负责判断做什么、为什么做、先做什么，并推动结果落地。 | 当你需要明确产品责任边界、定义产品目标或推动跨团队协作时使用。 |
| 2 | **Product** | 能够持续为一类用户解决特定问题并创造价值的解决方案，不一定是 App。 | 定义一个产品时，优先描述它解决的问题和用户价值，而不是功能清单。 |
| 3 | **User** | 实际使用产品的人。 | 做需求分析时先明确谁在使用，以及他在什么场景下使用。 |
| 4 | **Customer** | 购买、付费或做采购决策的人，可能与实际用户不同。 | B端产品尤其要区分使用者、决策者和付款者。 |
| 5 | **B端 / B2B** | 面向企业或组织提供产品和服务。 | 设计时通常需要考虑角色权限、组织流程、采购和交付。 |
| 6 | **C端 / B2C** | 面向个人消费者提供产品和服务。 | 更关注体验、增长、留存、传播和转化。 |
| 7 | **G端** | 面向政府或公共机构的产品。 | 常需要关注合规、招采、数据安全和复杂协作流程。 |
| 8 | **SaaS** | Software as a Service，软件即服务，通常通过订阅持续提供能力。 | 设计商业模式时关注订阅、续费、席位、使用量和服务成本。 |
| 9 | **Pain Point** | 用户在完成目标过程中真实存在的麻烦、损失或阻力。 | 不要把用户说出的解决方案直接当成痛点，要继续追问根因。 |
| 10 | **Scenario** | 用户在特定时间、地点、任务和约束下使用产品的具体情境。 | 写 PRD 前先描述核心使用场景。 |
| 11 | **Use Case** | 描述某个角色如何通过系统完成一个具体目标的用例。 | 用于澄清主流程、前置条件、异常情况和完成条件。 |
| 12 | **Persona** | 基于研究抽象出的典型用户画像。 | 用于统一团队对核心用户的理解，避免‘为所有人设计’。 |
| 13 | **User Story** | 以‘作为某类用户，我希望……，从而……’表达需求的方式。 | 用于敏捷团队拆解需求和验收。 |
| 14 | **JTBD** | Jobs To Be Done，用户真正想完成的任务或进步，而非表面功能需求。 | 当用户提出功能时，用它判断背后真正要完成的任务。 |
| 15 | **Value Proposition** | 产品向目标用户承诺的核心价值。 | 产品定位时回答：为什么用户要选择你而不是现有方案。 |

## 需求与设计

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 16 | **Requirement** | 需要被解决的用户、业务、合规或技术问题。 | 需求评审时区分问题本身与具体实现方案。 |
| 17 | **Requirement Pool** | 集中存放和管理待评估需求的需求池。 | 把所有反馈先入池，再统一评估优先级，避免临时插单。 |
| 18 | **需求优先级** | 决定哪些需求先做、后做或不做。 | 结合用户价值、业务价值、风险、成本和战略一致性判断。 |
| 19 | **RICE** | Reach × Impact × Confidence ÷ Effort 的优先级框架。 | 适合多个候选需求需要相对量化比较时使用。 |
| 20 | **MoSCoW** | Must / Should / Could / Won’t，用于按必要性给需求分层。 | 适合版本范围管理和资源有限时做取舍。 |
| 21 | **Kano Model** | 把需求分为基本型、期望型、兴奋型等，帮助理解满意度影响。 | 适合分析体验型功能和差异化价值。 |
| 22 | **MVP** | Minimum Viable Product，用最低成本验证最关键产品假设的最小可行方案。 | 重点不是‘功能少’，而是‘能验证核心假设’。 |
| 23 | **Prototype** | 用于验证结构、流程或交互的原型。 | 开发前用来发现交互问题并降低沟通成本。 |
| 24 | **Wireframe** | 低保真线框图，表达页面信息层级和基本布局。 | 用于快速讨论结构，不要过早陷入视觉细节。 |
| 25 | **Information Architecture** | 信息架构，定义内容、页面、功能之间如何组织和层级化。 | 复杂产品先做 IA，再做页面细节。 |
| 26 | **User Flow** | 用户为完成目标经过的一系列步骤。 | 用于优化路径长度、分支、阻塞点和转化。 |
| 27 | **Flowchart** | 用图形描述业务、系统或用户流程。 | 适合表达条件分支、异常处理和多角色协作。 |
| 28 | **Interaction Design** | 交互设计，定义用户与界面之间的操作和反馈机制。 | 关注操作是否可理解、可恢复、可预期。 |
| 29 | **UX** | User Experience，用户完成目标时的整体体验。 | 不仅是界面美观，还包括效率、理解成本、信任和情绪。 |
| 30 | **UI** | User Interface，用户看到和操作的界面。 | UI 是体验的一部分，不等于产品设计本身。 |

## 产品文档

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 31 | **PRD** | Product Requirements Document，描述为什么做、做什么、范围、流程、规则、验收和指标。 | 用于让研发、设计、测试等团队形成一致理解。 |
| 32 | **BRD** | Business Requirements Document，描述商业背景、目标、价值和约束。 | 适合重大项目立项或需要向业务决策者说明商业价值时。 |
| 33 | **MRD** | Market Requirements Document，描述市场、用户、竞争和机会。 | 适合进入新市场、定义新品类或做产品方向判断。 |
| 34 | **Roadmap** | 产品路线图，展示未来一段时间的目标、主题和关键版本。 | 用于对齐方向，不应退化成固定不变的功能排期表。 |
| 35 | **Product Vision** | 产品愿景，描述长期希望为用户和市场创造什么状态。 | 用来指导长期取舍和团队共识。 |
| 36 | **Product Strategy** | 产品战略，为实现愿景而选择的目标市场、价值主张和竞争路径。 | 回答‘我们选择在哪里赢，以及不做什么’。 |
| 37 | **Scope** | 项目或版本明确包含与不包含的范围。 | 写清 In Scope / Out of Scope 可显著减少需求膨胀。 |
| 38 | **Acceptance Criteria** | 验收标准，定义什么条件下需求算完成。 | 每个核心需求都应有可测试的完成条件。 |
| 39 | **Release Note** | 面向用户或团队说明某版本新增、优化和修复内容。 | 用于上线沟通和用户教育。 |
| 40 | **Changelog** | 按时间记录产品或系统变化的日志。 | 适合追踪版本历史和技术变更。 |

## 研发协作

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 41 | **Agile** | 敏捷开发，通过小步迭代、快速反馈降低不确定性。 | 适合需求变化快、需要持续验证的产品。 |
| 42 | **Scrum** | 一种常见敏捷框架，围绕固定节奏的 Sprint 推进。 | 用于组织迭代、站会、评审和复盘。 |
| 43 | **Sprint** | 固定长度的一次开发迭代，常见为 1–2 周。 | Sprint 内尽量保持目标稳定，避免无限插单。 |
| 44 | **Backlog** | 按优先级管理的待办需求或任务列表。 | 定期梳理，避免成为永不清理的‘需求仓库’。 |
| 45 | **Epic** | 较大的业务目标或需求主题，需要拆成多个 Story。 | 用于管理大范围能力建设。 |
| 46 | **Story** | 可在一个迭代中交付的用户价值单元。 | 要足够小、可验收、对用户有意义。 |
| 47 | **Task** | 实现 Story 所需的具体工作任务。 | 通常由研发、设计、测试进一步拆分。 |
| 48 | **Milestone** | 项目中的关键阶段性节点或成果。 | 例如 Beta 上线、正式发布、首批客户交付。 |
| 49 | **Iteration** | 基于数据和反馈不断改进产品的过程。 | 上线不是结束，而是进入下一轮验证。 |
| 50 | **Release** | 将一个版本正式交付给用户。 | 需要配合测试、监控、回滚和沟通方案。 |
| 51 | **Gray Release** | 灰度发布，先向少量用户或流量开放新版本。 | 用于控制风险并观察真实效果。 |
| 52 | **Rollback** | 新版本出现严重问题时恢复到上一稳定版本。 | 上线方案必须提前考虑是否可回滚。 |
| 53 | **Bug** | 产品行为与预期、设计或规则不一致的软件缺陷。 | 需要按严重度、影响范围和修复成本分级。 |
| 54 | **Blocker** | 会阻止项目继续推进的关键问题。 | 应明确责任人、解决路径和截止时间。 |
| 55 | **Tech Debt** | 为了速度或短期目标留下的技术妥协，未来需要偿还。 | 产品经理要理解短期收益与长期维护成本。 |

## 数据与增长

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 56 | **KPI** | Key Performance Indicator，衡量关键业务或绩效结果的指标。 | 指标要可衡量并与目标直接相关。 |
| 57 | **OKR** | Objectives and Key Results，目标与关键结果管理方法。 | O 描述方向，KR 描述可验证结果。 |
| 58 | **North Star Metric** | 北极星指标，最能代表用户持续获得核心价值的关键指标。 | 避免选纯流量指标，应与用户价值和长期增长相关。 |
| 59 | **DAU** | Daily Active Users，日活跃用户数。 | 要先定义什么行为才算‘活跃’。 |
| 60 | **WAU** | Weekly Active Users，周活跃用户数。 | 适合非每日高频产品。 |
| 61 | **MAU** | Monthly Active Users，月活跃用户数。 | 结合 DAU/MAU 可粗看使用频率和粘性。 |
| 62 | **PV** | Page View，页面被浏览的总次数。 | 一个用户多次访问会重复计数。 |
| 63 | **UV** | Unique Visitor，独立访问用户数。 | 用于看有多少不同用户访问，而非访问次数。 |
| 64 | **Retention** | 留存率，某批用户经过一段时间后仍继续使用的比例。 | 应按产品使用周期选择次日、7日、30日等口径。 |
| 65 | **Churn** | 流失率，用户停止使用、取消订阅或离开的比例。 | 需要定义何时算流失并分析原因。 |
| 66 | **Conversion Rate** | 转化率，从一个关键阶段进入下一个阶段的比例。 | 例如访问→注册、试用→付费。 |
| 67 | **Funnel** | 漏斗，把用户关键路径拆成多个阶段观察流失。 | 先找最大流失点，再结合定性研究解释原因。 |
| 68 | **CTR** | Click Through Rate，点击次数或点击用户占曝光的比例。 | 必须明确分母是曝光次数还是曝光用户。 |
| 69 | **ARPU** | Average Revenue Per User，平均每个用户贡献的收入。 | 用于商业化和用户价值分析。 |
| 70 | **CAC** | Customer Acquisition Cost，获得一个新增付费客户的平均成本。 | 需要把相关营销和销售成本计入口径。 |
| 71 | **LTV** | Lifetime Value，用户生命周期内预期贡献的总价值。 | LTV 与 CAC 应结合判断商业模型可持续性。 |
| 72 | **GMV** | Gross Merchandise Value，平台一定周期内的交易总额。 | GMV 不是收入，不能直接等同利润。 |
| 73 | **ROI** | Return on Investment，投入产出比。 | 用于比较不同项目、功能或增长动作的经济收益。 |
| 74 | **A/B Test** | 将用户随机分组，对不同方案进行控制实验。 | 需要提前定义假设、主指标、样本和实验周期。 |
| 75 | **Cohort Analysis** | 按共同起点或特征分组，比较不同批次用户后续表现。 | 特别适合分析留存、付费和版本影响。 |

## 商业与增长

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 76 | **PMF** | Product-Market Fit，产品与市场需求形成较稳定匹配。 | 常通过高留存、自然增长、强需求和付费意愿等信号综合判断。 |
| 77 | **Growth** | 通过产品、渠道、运营等手段持续提升核心业务指标。 | 增长不是单纯拉新，要覆盖激活、留存、变现和传播。 |
| 78 | **Growth Loop** | 用户行为能够持续带来下一轮新增或价值的增长闭环。 | 例如创作者产内容→内容获客→新用户成为创作者。 |
| 79 | **Acquisition** | 获客，让目标用户第一次进入产品。 | 评估渠道质量不能只看量，还要看后续留存和价值。 |
| 80 | **Activation** | 用户第一次真正感受到产品核心价值的关键时刻。 | 需要明确产品的 Aha Moment。 |
| 81 | **Monetization** | 把用户价值转化为收入的机制。 | 订阅、按量、广告、交易佣金等都属于商业化方式。 |
| 82 | **Subscription** | 订阅制，用户按周期持续付费使用产品。 | 重点关注续费、流失、套餐结构和单位成本。 |
| 83 | **Freemium** | 基础能力免费，高级功能或更高额度收费。 | 免费层应能让用户感受价值，但又保留清晰升级理由。 |
| 84 | **Upsell** | 让已有客户购买更高版本、更多席位或更大额度。 | B端和 SaaS 中常与客户成功结合。 |
| 85 | **Unit Economics** | 单位经济模型，分析单个用户、订单或客户是否赚钱。 | 典型关注 LTV、CAC、毛利、服务成本和回收期。 |

## AI产品

| # | 术语 | 大白话解释 | 开发时怎么用 |
|---:|---|---|---|
| 86 | **LLM** | Large Language Model，大语言模型，可理解和生成自然语言及多种内容。 | AI 产品经理要理解不同模型在质量、速度、成本、上下文和工具调用上的差异。 |
| 87 | **Prompt** | 发送给模型的指令、上下文和约束。 | 不要把产品效果完全依赖‘神奇提示词’，应结合流程、数据、工具和评测。 |
| 88 | **Token** | 模型处理文本等内容时使用的计量单位，也是上下文和成本的重要基础。 | 设计长文本产品时需关注输入输出 Token 和成本。 |
| 89 | **Context Window** | 模型单次请求可以处理的上下文容量。 | 上下文更大不等于一定更好，仍需控制信息质量和注意力稀释。 |
| 90 | **RAG** | Retrieval-Augmented Generation，先从外部知识源检索相关信息，再让模型基于检索内容生成答案。 | 适合需要私有知识、最新信息和可追溯依据的场景。 |
| 91 | **Embedding** | 把文本、图像等内容映射成向量，以表示语义特征。 | 常用于相似度搜索、聚类、推荐和 RAG。 |
| 92 | **Vector Database** | 用于存储和检索向量的数据库或向量检索系统。 | RAG 中常用于根据语义找到相关知识片段。 |
| 93 | **Agent** | 能够围绕目标进行理解、规划、调用工具、观察结果并继续行动的 AI 系统。 | 不要把任何聊天机器人都叫 Agent，关键在于可执行和闭环。 |
| 94 | **Tool Calling** | 模型按照结构化参数调用外部工具或函数的能力。 | 用于连接搜索、数据库、邮件、日历、业务 API 等。 |
| 95 | **MCP** | Model Context Protocol，用统一协议让模型或 Agent 接入外部工具、资源和上下文。 | 适合需要标准化连接多种数据和工具的 Agent 产品。 |
| 96 | **Fine-tuning** | 在基础模型上用特定数据继续训练，以调整输出行为或专业能力。 | 不要在 RAG、Prompt、工具调用能解决问题时默认选择微调。 |
| 97 | **Hallucination** | 模型生成貌似合理但事实错误、无依据或虚构的内容。 | 高风险场景需要用检索、工具、约束、引用和人工审核降低风险。 |
| 98 | **Evaluation / Eval** | 系统化评估 AI 输出质量、任务成功、稳定性和风险的方法。 | 应建立测试集、指标、人工标准与自动评测组合。 |
| 99 | **Latency** | 从用户发出请求到获得结果的等待时间。 | AI 产品常需要在质量、成本和速度之间做权衡。 |
| 100 | **Task Success Rate** | AI 在目标定义下成功完成任务的比例。 | 比单纯调用次数更接近 Agent 产品的真实用户价值。 |
