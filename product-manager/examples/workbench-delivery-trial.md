# 匿名化教师工作台｜跨版本交付判断示例

以下为用于说明 Skill 路由和验收门槛的匿名化、合成场景，不对应可识别的客户或生产系统，也不是已完成的真实用户验收。

## 输入问题

“把工作台做完整，下周能否上线？”

## 路由与现实快照

- 路由：`delivery-os`，辅以版本范围与体验判断；阶段为 BUILD→TEST。
- 旧工作台有较广教务功能，但使用独立的旧数据环境；不能把旧功能目录当作新产品现状。
- 候选教师工作台具备登录、班级与学生资料、普通作业发布、提交列表和文字批阅，并与学生端共享新环境。
- 若干自动测试通过、匿名访问被拒绝；真实身份下教师→学生→家长的正向、失败及撤权路径仍待验收。
- 重试去重、跨设备恢复、统计边界、告警和回滚仍需验证。收费、排课、考勤只在旧系统存在。

## 推荐决定

“完整”先定义为教师、学生、家长之间的核心教学任务闭环可靠可用，而非立即照搬旧系统全部菜单。先做隔离测试班的登录、资料编辑、作业发布、学生提交、教师退回/通过、家长可见及权限撤销验收；通过后再按岗位频率决定排课、考勤、家长绑定和课时等运营模块。收费/退款等高风险模块不自动进入首个可运营版本。

## Skill 回归门槛

合格输出应：区分旧/新/演示环境；不把 HTTP 200 或自动测试说成正式运营；写清残余边界；有角色任务、权限、跨端证据与明确的 Non-goals。若直接生成“大而全”页面清单或宣称正式上线，视为失败。

这个场景仅说明评估方法，不证明其他模型运行时总能稳定遵循。后续仍需隔离盲测。
