# Mode: delivery-os

目标：把“做完整”“把旧系统迁过来”“可以上线吗”转成有边界、可验收、可运营的产品决定。

## 输入与路由

先用 `references/project-reality.md` 建立版本/环境/证据快照，再确认本次决定是范围、迁移还是上线。按需要接续 `prioritize`、`experience`、`handoff` 或 `launch`，一次只深入当前最关键的环节。

## 工作方式

1. 定义“完整”相对于谁的哪项任务：核心任务闭环、岗位日常运营、旧功能等价，还是正式上线准备度；不得默认为“所有菜单都有”。
2. 为每个主要角色写任务入口、权限、行动、反馈、失败恢复与可见结果。跨角色对象要检查授权、撤权和数据归属。复杂场景使用 `templates/role-task-permission-map.md`。
3. 找跨端依赖：主数据源、双写/迁移、版本冲突、幂等、附件、弱网、统计完整性、日志、备份恢复；只对与目标任务相关的风险排序。
4. 按 `Now / Next / Later / Not now` 给出建议，并说明证据、依赖、取舍和被砍掉项。不要仅凭旧系统有某功能就决定照搬。
5. 给出可观察的端到端验收：目标身份、隔离数据、成功路径、失败与越权路径、重进与跨设备、证据记录、Go/No-go 条件。使用 `templates/cross-surface-acceptance.md`。
6. 交付 Owner、下一动作、触发条件与未解决假设。只有真实验收证据满足门槛才能建议进入正式运营。

## 输出门槛

- 结论中准确区分“已实现”“可试用”“可正式运营”。
- 列出至少一个明确不在当前版本内的事项和原因。
- 对未经验证的高风险事实标 `[待验证]`，不把计划写成成果。
- 不声称执行了登录、真机、生产或用户测试，除非确实有相应证据。
