# Operating Loop｜状态读取、证据更新与决策写回

本协议只规定跨次任务怎样保持判断可追溯；端到端产品阶段与工作节奏见相应 `workflows/`。它不自动维护项目状态或监控业务指标。没有持久文件时，可以在本次回复中完成同样的轻量记录。

## 1. 读取当前状态

复杂项目任务按需读取现有 `.pmcontext.md`、证据记录、决策日志及当前版本交付物。先确定本次决策、适用产品版本/环境/用户群、最近可信观察日期及此前已确认的决策。缺文件时只标缺口，不据此假设项目从零开始；旧版本证据不自动证明新版本现状。

## 2. 维护证据，不覆盖历史

影响决策的关键主张应追到具体来源、观察日期和适用范围。按 `templates/evidence-ledger.md` 标明事实、推断或假设及重新核验触发条件。发现矛盾时并列记录并标争议；新观察推翻旧结论时，新增证据 ID，给旧记录标 `SUPERSEDED` 并相互引用。不要把“自动测试通过”改写为“真实用户验收通过”。

证据深度与风险成比例：简单可逆的建议在答复中标来源与假设即可；高成本、不可逆或跨角色/跨端决定，应保留可定位的证据索引。外部易变事实遵守 `references/living-sources.md` 的核验规则。

## 3. 让建议进入可复查的决策状态

模型方案先是 `PROPOSED`。仅在负责人明确确认或已有可核验授权决策记录时转 `COMMITTED`；记录负责人、选择及放弃的选项、预期结果、护栏和复查触发条件。触发后，用实际指标、用户反馈或验收证据追加 `REVISITED` 事件，写明与预期的差异及继续、调整或停止的下一动作；停止记 `STOPPED`，改为新决定时旧记录标 `SUPERSEDED` 并引用新 ID，被否决的建议记 `REJECTED`。未发生的结果保持 `[待验证]`。见 `references/decision-contract.md` 与 `templates/decision-log.md`。

## 4. 写入边界与结束条件

默认只读。只有用户明确要求建立/更新项目记录，或本次已授权交付物包含这些文件，才写回；写前确认目标位置、保留已有内容和状态历史，写后说明修改了什么、哪些仍未获确认。未经授权时在回复中给出拟议增量，不自行建立“长期记忆”。订阅、定时复查、联系用户、改生产数据或发布仍需单独授权。

每次复杂任务以最小闭环结束：**当前判断及证据时点 → 决策状态 → Owner / 下一动作 / 复查触发条件**。关键证据冲突足以改变高风险决定时停在 `NEEDS_CONTEXT`；可安全推进时只给带 `[假设]` 的 `PROPOSED` 草稿。不要为维持仪式感制造文件或例行更新。
