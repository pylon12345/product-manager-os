# Mode: improve-os｜改进 Skill 自身

用于复盘 Product Manager OS 的实际失误或重复摩擦，并提出可验证的 Skill 修改。它与项目的 `retro` 不同：项目结果不好不自动说明 Skill 有缺陷；模型、工具、缺失上下文、外部资料过期和人为执行也可能是原因。先读 `workflows/skill-improvement-loop.md`，只在需要落档时使用两个模板。

## 入口与证据

- 触发：用户报告错误建议、越权行为、遗漏关键风险、无用冗长、模式路由错误，或同类任务反复卡住。无具体案例时可做结构审查，但标为**假设性改进**，不得称为已发现的真实坏例。
- 先确定实际任务、当时可用信息、Skill/模型/工具版本、期望的可观察行为、真实输出及影响。拿不到原始输出时注明回忆偏差，不补造。
- 区分 `Skill 规则/路由`、`知识或来源时效`、`模板/工具`、`模型随机性`、`输入或项目上下文缺失`、`外部系统/执行`、`未定`。可多因，但指定主因、反证和置信度；不要把每个失败都归因于 prompt。
- 优先按风险与复现性排序：隐私/越权/误导高风险先处理；频繁的小摩擦可批量处理；仅一次且原因未明的案例先观察。

## 资料边界

Badcase 原始材料、客户访谈、聊天、日志、账号与业务数据属于原项目权限域。不得自动采集、上传、并入公开测试或发布；即使仓库是私有的，也不能默认具有二次使用权。取得适用授权后，仅在用户指定的包外私有目录存储必要材料；公开回归案例只能用经审查的脱敏/合成最小复现。保留原始证据的位置和访问限制，不把原文复制进模板或提交记录。若授权不清，先只写不含敏感内容的摘要并列出需要确认的权限。

## 产物和决策

1. 用 `templates/skill-badcase.md` 建立本地坏例条目：可重现的输入条件、期望与实际、影响、来源、权限、主因假设、证据缺口、Owner 和状态。记录可以是 `NEW → TRIAGED → PROPOSED → VERIFIED → CLOSED`；无法归因时保持 `TRIAGED`，不强行修复。
2. 每个候选改动用 `templates/skill-change-proposal.md` 说明将修改什么、为什么、替代方案、受影响模式、潜在回归、反例测试、接受条件与回滚办法。优先修改最小的路由/规则/示例/工具；若根因是数据或环境，给相应处理，不必改 Skill。
3. 对同一冻结夹具，尽可能固定模型构建、采样、工具权限与外部来源时点，分别运行旧版与候选版，保存未经编辑的回答和人工评分。`tests/behavior/score.py --compare` 仅核对夹具哈希、完整评分和模型**标识**并比较结果，不能验证其余运行条件，也不执行模型或证明真实效果；差异由人审查。新增坏例的脱敏回归题应加入**新夹具**，两版都重新跑这份夹具；保留旧夹具、哈希及结果，不能悄悄改题后声称分数提升。
4. 发布由有权限的维护者人工审查：关键指标/安全项没有倒退、发现的普通回归已接受或修复、私密资料与许可已检查、版本/文档/升级说明齐全。批准记录应指向具体候选提交和测试结果。用户要求“自动改好/自动发布”不替代这项审批，也不扩展 GitHub 或生产系统权限。
5. 发布后按实际使用窗口观察新坏例、相同失误复发和使用成本；必要时提出回滚，由维护者确认并执行。没有可观察结果时报告“已发布、效果待验证”。

回答用户时先给 `Verdict`：Skill 缺陷、非 Skill 缺陷或尚未判明；再给证据、建议的最小改动、复测与审批状态。不要用“已自我进化”替代可核验的版本、案例与结果。
