# Decision Contract

复杂任务先建立决策契约，防止把“写文档”误当成完成产品工作。

## 必填字段

- **Decision**：本次要做或支持什么决定。
- **Decision owner**：谁承担最终取舍，不把责任交给框架或模型。
- **Deadline / reversibility**：何时决定，是否可逆，回滚成本如何。
- **Known / unknown**：事实、关键假设、必须验证的未知数。
- **Options**：至少包含现状/不做；重大决策通常比较 2 个以上可行选项。
- **Criteria**：用户价值、战略匹配、收益/成本、风险、交付约束。
- **Evidence bar**：证据强度与成本、不可逆性和风险匹配。
- **Recommendation**：明确选择、放弃什么、为什么现在。
- **Commit / revisit / kill**：承诺、复查触发条件和停止条件。

## 使用规则

- 简单请求可在内部快速建立，不要求用户填写表格。
- 缺少信息但可安全草拟时，标记 `[假设]` 并继续。
- 只有缺失信息会改变高成本、不可逆或高风险决策时才阻塞。
- 数字评分只能压缩有依据的判断，不能替代证据。
- 所有建议都要区分 `现在做`、`验证后做`、`不做`。
- 模型给出的 Recommendation 默认为 `PROPOSED`，不代表团队已承诺。只有决策负责人明确确认，或有可核验的授权决策记录，才标 `COMMITTED`。
- 决策记录保留稳定 ID、适用版本/环境、证据索引、负责人、预期结果和复查触发条件。复查时追加实际结果与后续动作，标 `REVISITED`；不改写原始依据，也不把未发生的结果写成已发生。终止状态：负责人否决建议标 `REJECTED`；触发 kill 条件或负责人决定停止标 `STOPPED`；被新决策取代标 `SUPERSEDED` 并引用新 ID。
- 未获写入授权时，只在回复中给出建议记录，不自动修改项目文件。持续协议见 `references/operating-loop.md`。

## 输出最小闭环

1. 结论先行。
2. 关键证据与置信度。
3. 被拒绝选项及核心原因。
4. 风险、护栏和回滚。
5. Owner、下一动作、截止时间或触发条件。
